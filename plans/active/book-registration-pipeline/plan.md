# 책 등록 파이프라인 안정화 계획

## Goal

AI 보조 등록과 앱의 수동 등록이 같은 이미지 처리 계약을 사용하도록 책 등록 흐름을
정리한다. 책 순서·용도·오디오 필드·주차를 단일 배치 명세에서 확정하고, 브라우저
자동화 없이 표지를 작은 용량으로 처리한 뒤 저장 전후 결과를 재현 가능하게 검증한다.

이 계획은 다음 세션의 작업 계약이다. 이번 계획 작성에서는 앱 코드·DB 스키마·운영
데이터를 변경하지 않는다.

## Context

현재 앱은 `lib/cover-image.ts`의 브라우저 `canvas.toDataURL()`로 표지를 긴 변 960px,
JPEG 품질 0.72로 변환한다. `app/reading-manager-client.tsx`가 이 함수를 직접 호출한 뒤
`lib/supabase/reading-store.ts`를 통해 `books.cover`에 data URL 전체를 저장한다.
별도 이미지 등록 API나 서버 이미지 처리기는 없다.

AI 보조 등록에서는 같은 결과를 재현하려고 로컬 Playwright/Chromium에서 브라우저
함수를 실행했다. 결과 이미지는 실제로 축소됐지만, 배치 등록이 브라우저 자동화에
의존했고 샌드박스 실패와 불필요한 실행 복잡성이 생겼다. 또한 사진·책 순서·링크·
배정 후보·결과 기록이 대화와 여러 임시 파일에 흩어져 다음 문제가 발생했다.

- 지온 읽기 책 순서를 잘못 저장한 뒤 수정했다.
- 읽기/정따 URL 필드가 중간 상태에서 혼동됐다.
- DB 완료와 실제 앱 확인을 같은 “완료”로 표현하기 쉬웠다.
- 큰 base64 JSON 전달에서 출력 잘림과 바이트/문자 길이 혼동이 발생했다.
- 이미지가 축소됐다는 해상도·바이트 증거를 사용자에게 즉시 보여주지 못했다.

## Working Contract

### 확정한 결정

1. 이미지 압축을 위해 Playwright, Chromium 또는 브라우저 MCP를 사용하지 않는다.
2. 원본 사진은 보존한다. 표지 보정은 회전·원근·외부 배경 제거로 제한하고 이미지
   압축과 별도 단계로 취급한다.
3. Node에서 실행 가능한 공용 이미지 처리기를 만든다. 앱의 등록 경로와 AI/CLI 등록
   경로가 같은 처리 계약을 사용해야 한다.
4. 책 순서·아동·용도·주차·사진·오디오 필드와 URL을 하나의 배치 명세에 먼저 확정한다.
5. 준비 단계는 DB를 변경하지 않는다. 저장 전 날짜별 책 배치와 처리 후 이미지
   해상도·바이트·해시를 보여준다.
6. 저장 단계는 소유·중복·활성 상태·필수 오디오·기간 충돌을 다시 확인한다.
7. 결과 상태를 `prepared`, `applied`, `db_verified`, `app_verified`로 구분한다.
8. 기존 `owner_user_id` 경계와 RLS를 유지한다. service-role 키를 클라이언트나 배치
   명세에 넣지 않는다.

### 다음 세션에서 결정할 항목

| 결정 | 권장 출발점 | 결정 근거 |
| --- | --- | --- |
| 저장 위치 | 1차는 기존 `books.cover` data URL 유지 | 스키마·RLS·기존 데이터 변경 없이 파이프라인 문제부터 해결한다. |
| 장기 저장 | Supabase Storage 별도 후속 검토 | base64는 바이너리보다 약 33% 크며 Postgres 행을 비대하게 만든다. Storage 정책과 이전 전략이 필요하다. |
| 최대 해상도 | 실제 모바일 표시 폭 측정 후 720~960px 비교 | 작은 제목의 가독성을 보지 않고 숫자를 고정하지 않는다. |
| 포맷 | JPEG와 WebP를 대표 표지로 비교 | WebP 절감 효과와 현재 표시 호환성을 수치로 확인한다. |
| 목표 용량 | 표지당 80~120KB 후보 | 품질 하한과 해상도 단계 축소 규칙을 함께 정해야 한다. |
| 등록 경로 | 서버 API/Server Action과 CLI가 공용 처리기를 호출 | 브라우저 canvas를 기준 구현으로 두지 않는다. 인증·요청 크기를 먼저 검토한다. |

Storage 전환을 선택하면 이 계획을 갱신하고 `ewd-supabase-change` 절차로 Storage 정책,
URL 전략, 실패 시 정리와 기존 표지 이전을 별도 설계한다. 1차 구현에서 기존 표지의
일괄 재압축은 하지 않는다.

## Pipeline

```text
원본 사진
  → 배치 명세 작성·검증
  → 표지 기하 보정(필요한 사진만)
  → 공용 이미지 처리기(방향·축소·인코딩·용량 제한)
  → 책/배정 dry-run과 사용자 확인이 필요한 모호성 표시
  → 저장 직전 소유·중복·충돌 재검사
  → 보호된 적용
  → 별도 재조회로 전체 필드·이미지 해시 비교
  → 실제 로그인 앱 확인
```

### 단계별 책임

- **Prepare**: 입력을 정규화하고 처리된 표지와 날짜별 배정 후보를 생성한다. DB 쓰기 없음.
- **Apply**: 준비된 명세의 해시를 확인하고 허용된 신규 행만 저장한다. 중간 입력을
  재해석하거나 책 순서를 다시 추론하지 않는다.
- **Verify**: 책 메타데이터, 표지 길이·해시, 배정 전체 필드를 독립 재조회한다.
- **App check**: 로그인된 앱의 표시와 오디오 실행을 확인한다. DB 검증으로 대체하지 않는다.

## Local Glossary

이 용어들은 등록 파이프라인 내부 용어이며 현재 앱의 학습 도메인 모델을 변경하지 않는다.

| 용어 | 의미 |
| --- | --- |
| 배치 명세 | 한 요청의 아동·주차·책 순서·용도·사진·URL 필드와 처리 설정을 담는 단일 기준 입력. |
| 원본 사진 | 사용자가 제공한 변경하지 않는 파일. |
| 보정 표지 | 원본에서 회전·원근·외부 배경만 정리한 중간 산출물. |
| 처리 표지 | 방향 보정, 크기 축소, 메타데이터 제거와 인코딩이 끝난 저장 후보. |
| 준비된 배치 | 검증된 처리 표지와 날짜별 배정 후보가 있고 DB에는 아직 반영하지 않은 상태. |
| 적용된 배치 | 책/배정 쓰기 요청이 DB에서 성공한 상태. 재조회 검증 전일 수 있다. |
| DB 검증 완료 | 저장 행의 모든 요청 필드와 표지 해시가 준비된 배치와 일치한 상태. |
| 앱 확인 완료 | 로그인된 실제 앱에서 표지·할 일·오디오 동작을 확인한 상태. |

전역 `CONTEXT.md`나 ADR은 아직 만들지 않는다. 위 용어는 구현 세부 흐름이고,
Storage 여부와 공용 등록 경로가 확정되지 않아 되돌리기 어려운 아키텍처 결정을 내리지 않았다.

## Out of Scope

- 기존 표지 전체의 일괄 재압축 또는 자동 마이그레이션.
- AI가 책·순서·주차를 임의로 선택하는 기능.
- 생성형 이미지로 표지 내용을 복원하거나 누락 영역을 만드는 기능.
- QR 인식 알고리즘 전면 교체.
- 상시 폴더 감시, 자동 배포, Git commit/push.
- 이 계획과 무관한 기존 테스트·UI·PWA 변경.

## Required Verification

| 시나리오 | 합격 기준 |
| --- | --- |
| 휴대폰 원본 사진 | EXIF 방향을 반영하고 긴 변·포맷·품질·목표 용량 계약을 만족한다. |
| 작은 이미지 | 확대하지 않고 내용과 비율을 유지한다. |
| 투명 이미지 | 명시한 배경색으로 합성되며 예기치 않은 검은 배경이 생기지 않는다. |
| 매우 큰 이미지 | 픽셀/파일 제한에서 안전하게 거부하거나 처리하고 메모리 폭증을 방지한다. |
| 잘못된 파일 | 이미지가 아닌 파일, 손상 파일, 빈 파일을 DB 쓰기 전에 거부한다. |
| 용량 초과 | 정한 품질 하한과 해상도 축소 규칙을 적용하거나 명시적 실패로 보고한다. |
| 순서 변경 | 배치 명세의 책 순서가 날짜별 배정에 그대로 반영되고 dry-run에 보인다. |
| URL 필드 | 읽기와 정따 URL이 용도와 일치하지 않으면 준비 단계에서 거부한다. |
| 중복/충돌 | 제목·URL 중복과 같은 아동/활동/기간 충돌을 적용 직전에 다시 검출한다. |
| 부분 실패 | 결과가 불명확하면 재조회하고 확인된 누락만 처리한다. 전체 배치를 재실행하지 않는다. |
| 결과 상태 | DB 검증과 로그인 앱 확인이 별도 상태로 기록된다. |

테스트는 `docs/testing-guidelines.md`의 Given–When–Then 형식을 따른다. 좁은 검사부터
실행하고 최종적으로 `npm run verify`를 통과한다. 이미지 처리 테스트는 Playwright를
사용하지 않고 고정 fixture와 Sharp 메타데이터·해시·용량 assertion으로 검증한다.

## ADR Decision

현재는 ADR을 만들지 않는다. `books.cover` 유지와 Storage 전환 중 하나를 선택하고,
그 선택이 장기간 저장·보안·이전 비용을 결정할 때 ADR 필요성을 다시 판단한다.
